Regras de ouro

São seis, e a primeira explica a arquitetura inteira do kit.

Componente é tag

Não existe classe de componente. Botão, campo, card, alerta, chip e item de menu são <lc-button>, <lc-input>, <lc-card>, <lc-alert>, <lc-badge>, <lc-menu-item>.

Uma forma só de usar o kit: quem escreve protótipo não decide, a cada elemento, se procura classe ou tag. E erro de uso passa a aparecer — <lc-buton> fica visível na tela e no console, enquanto class="lc-bton" não produzia nada e atravessava revisão.

O custo está registrado no ADR 0001, e é real: portar uma view do legado deixou de ser renomear classe e passou a ser reescrever markup.

Duas exceções. A tabela continua <table class="lc-table"> — marcada com classe na navegação — porque o parser HTML expulsa elemento desconhecido de dentro de <table>. E utilitários e tipografia (.lc-stack, .lc-quiet, .lc-h1) seguem classe, porque não são componentes disfarçados.

As outras cinco

  1. Nunca reestilize componente por dentro. Use atributo, ::part() ou a custom property documentada no JSDoc do componente.
  2. Tag custom nunca é self-closing. <lc-icon name="x"></lc-icon>, jamais <lc-icon /> — o parser HTML engole o resto do markup.
  3. Nenhum valor literal de cor ou medida no protótipo. Use token (var(--lc-space-m)). Literal quebra na troca de tema, que é a razão de o kit existir.
  4. Textos de UI em pt-BR.
  5. Ícone sempre por <lc-icon>, nunca SVG inline nem emoji.

Quando a tag aparece como texto cru

Nesta ordem:

  1. A página está em file://. ES modules exigem HTTP. Sirva por um servidor.
  2. Caminho errado do loader.js ou do lc.css. Confira a aba Network.
  3. Erro de sintaxe em algum componente — a exceção aborta o módulo e nenhuma tag se registra. Rode node tools/check-syntax.mjs.
  4. Duas cópias do kit na página — procure o aviso [lc-components] no console.
  5. Tag self-closing — veja a regra 3 acima.
